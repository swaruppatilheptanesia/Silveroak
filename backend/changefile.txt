
# Bugfix: TPO Admin verification tab (/admin/students?tab=verification) — Posting Type now shows & filters by registered interest.
# Problem: the "Posting types" line and the top Posting-Type filter were driven by the student's job
# applications. But verification is a prerequisite to applying, so pending students have NO applications —
# only registered interests. Result: posting type showed "—" (couldn't tell which program the student
# enrolled in / showed interest in) and the filter returned nobody for pending students.
# Fix:
#  - Frontend (VerificationTab.tsx): new getStudentPostingTypeChips() derives posting types from
#    student.interests[] (each already carries a human label via INTEREST_LABELS), deduped by label, with a
#    fallback to application-derived types (formatPostingTypeLabel) for already-applied/re-verification cases.
#    Row renders them as secondary Badges; the Review dialog gains a "Posting Types / Interests" section
#    listing each interest label + registered date. (Dropped the unused PostingTypeBadge import.)
#  - Backend (admin.service.ts): getStudents resolves the posting-type master's value when
#    posting_type_master_id is supplied; buildStudentWhere now matches posting_type_master_id as an OR of
#    applications.posting.posting_type_master_id OR interest_registrations.interest_type == masterValue
#    (case-insensitive). Inclusive/additive — the shared student list also surfaces interested-but-not-applied
#    students when filtered by posting type. interest_type==master.value is the same assumption the existing
#    InterestLists filter relies on. NO migration (query logic only).
